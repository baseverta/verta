# 02 — Trabalhando com n8n

## Regra número um: editar por API, conferir por releitura

Todo workflow é editado por `PUT /api/v1/workflows/:id` e **conferido com um
`GET` imediatamente depois**. Nunca confie no status 200 do PUT: releia e verifique
que o que você queria mudar está lá.

Isso não é preciosismo. Uma vez editamos a partir de uma cópia desatualizada e o PUT
sobrescreveu — apagando um recurso inteiro que já estava pronto. O ciclo correto é
sempre **GET → alterar em memória → PUT → GET de conferência**, nessa ordem, sem
reaproveitar um JSON buscado minutos antes.

## O bug que mais nos mordeu (cinco vezes)

**Sintoma:** você insere um node no meio de uma cadeia que funcionava e algo depois
começa a devolver `undefined`, ou o workflow segue sem fazer nada.

**Causa:** o node seguinte usava `$json` implícito. `$json` é *o item do node
anterior* — ao inserir alguém no meio, o "anterior" mudou de identidade.

**Regra:** em Code node, **nunca** leia `$json` para pegar dado de um node
específico. Sempre referência explícita por nome:

```js
// frágil — quebra silenciosamente quando alguém insere um node antes
const body = $json.body || $json;

// correto — sobrevive a qualquer reordenação
const body = $('Webhook Mensagem WhatsApp').item.json.body
          || $('Webhook Mensagem WhatsApp').item.json;
```

Isso torna o nome do node parte do contrato — ver protocolo 07 sobre renomear node.

## Limitações do sandbox do Code node

| Limitação | Consequência prática |
|---|---|
| Não expõe `crypto` por padrão | precisa de `NODE_FUNCTION_ALLOW_BUILTIN=crypto` no docker-compose da VPS |
| Não lê Data Table | config precisa entrar por um node `dataTable` antes e ser lida com `$('Ler Config').all()` |
| Não lê credencial | segredo de assinatura fica hardcoded no código do node |

O padrão para ler config:

```js
const cfg = Object.fromEntries(
  $('Ler Config Pipedrive').all().map(i => [i.json.chave, i.json.valor])
);
```

## Nodes que não fazem o que o nome promete

**Google Drive `move` não move.** A operação existe, retorna sucesso e não faz nada.
Use HTTP Request cru — ver protocolo 05.

**Upload de arquivo exige binário.** Node de upload do Drive não aceita texto do
`$json`. Precisa de um `convertToFile` antes (`operation: toText`, `sourceProperty`,
`options.fileName` e `mimeType`), e então `inputDataFieldName: 'data'`.
Sintoma sem isso: *"Make sure that the previous node outputs a binary file"*.

## Variables não existem para nós

`Variables` do n8n exige licença Enterprise — a API devolve `403 feat:variables`.
Toda config compartilhada vai para **Data Table**. A tabela `pipedrive_config`
(id `X9RaPDBvQPvSflHM`) é o lugar de chaves de campo, IDs de etapa, etiquetas, IDs
de pasta do Drive e URLs de formulário.

**Exceção deliberada:** o workflow de conversa do WhatsApp mantém cópias inline dos
mapeamentos. Ele é caminho quente — o cliente está esperando resposta — e uma ida
extra ao banco por mensagem não se paga. Se mudar um mapeamento, mude **nos dois
lugares**.

## Armadilhas da API do n8n

**`limit` acima de 250 não dá erro visível.** A resposta vira `{"message": "..."}`
em vez de `{"data": [...]}`. Se seu script trata `data` como array, ele lê "vazio" e
você conclui que a tabela está vazia — foi exatamente o susto que tivemos com a
`pipedrive_config` (54 linhas, aparentemente zero). **Sempre confira que a resposta
tem `data` e que é array** antes de concluir qualquer coisa a partir de uma lista vazia.

**A API pública não move workflow entre pastas.** Organização de pastas é manual,
na interface.

## Organização em pastas

Uma pasta por **ferramenta que dispara o evento** — `Pipedrive`, `WhatsApp`,
`Typeform`, `Fathom` — e uma pasta `Rotinas` para tudo que roda por agendamento.

A lógica: quando algo não disparou, você sabe onde procurar antes de abrir qualquer
coisa. Se era reação a ação externa, está na pasta da ferramenta. Se era para rodar
no horário, está em `Rotinas`. Workflow novo nunca fica solto na raiz.

## Diagnóstico de execução

Ao investigar uma falha, olhe `runData` da execução, não só a mensagem de erro:

- **Quantas vezes cada node rodou.** Um node com 2 execuções quando devia ter 1
  denuncia conexão paralela sobrando — foi assim que achamos um bug em que "Montar
  SQLs" alimentava o mesmo node por dois caminhos, e o segundo carregava campo velho.
- **`source.previousNode`** mostra de onde cada execução veio.
- **A ordem dos nodes percorridos** mostra onde parou. Parada silenciosa no meio
  quase sempre é query com zero linhas (ver protocolo 03).

## Erros que já cometemos

**Conexão paralela esquecida.** Ao reconectar uma cadeia, a conexão antiga ficou.
O node rodava duas vezes, uma delas com dado velho, e gravava lixo. Ao reconectar,
**substitua** a entrada em `connections`, não adicione.

**Escapar código dentro de `node -e` no shell.** Perdemos tempo com regex que não
casava por causa de escaping do bash. Regra: script de manutenção vai para **arquivo
`.js`**, nunca inline no shell.

**Confiar em busca textual para achar dependência.** Um `grep` nos workflows não
enxerga o que o banco chama de dentro dele mesmo — ver protocolo 03.
